# 動画 URL 解決サーバーの仕様

`videourl` モジュールが、手元の `yt-dlp` の代わりに叩く HTTP の口を定める。
サーバー自体は別に実装する。

## サーバーを別に置く理由

`yt-dlp` は nsig の解決に JS ランタイム（deno）を要求する。
無いと URL は取れるのに、再生時に HTTP 403 で弾かれる。
解決自体は成功して見えるので気付きにくい。
deno の初回取得は 40MB 近い。

**手元に yt-dlp と deno を置かずに済むことが、この機能の値打ちそのものである。**
だから遅くなるのは仕様として受け入れる。
実測で手元の 3 倍かかる（後述）。

解決の要求を手元の回線から出さずに済むことも動機である。
YouTube が弾くのは抽出の側（動画のページと player の JS を繰り返し叩く動き）で、
`googlevideo` から映像を取る動きではない。
その抽出をまとめてサーバーへ寄せられる。

## 責任の分け方

サーバーは `yt-dlp -J` を 1 回走らせて、生の JSON をそのまま返す。
それ以外は全部クライアントに残る。

| やること | 担当 |
|---|---|
| `yt-dlp -J` を走らせて生 JSON を返す | サーバー |
| どのクライアントで叩くか決める | クライアント |
| フォーマットの選別（HLS と progressive と音声だけ） | クライアント |
| 素の GET で本当に取れるかの確認 | クライアント |
| 画面へ出す文言とラベル | クライアント |

**選別をサーバーに置かないことが、この設計で一番効いている決め事である。**
どのクライアントで何が取れるかは実測で動いてきた部分で、`android` は 206 を返すのに `mweb` と `web_safari` は 403 になる、という具合に変わる。
規則が 2 か所にあると、片方だけ古くなったときに手元と外で振る舞いが分岐する。
生 JSON を返せば、分岐する余地がそもそも無い。

署名と nsig は `yt-dlp -J` の中で解ける。
サーバーに deno が要るのはこの計算のためで、返る JSON の `formats[].url` は解いたあとの最終 URL である。
サーバー側で追加の手順は要らない。

取れた URL は要求元の IP に紐づかない。
VPS で解決した URL が別の回線からそのまま取れることを確認してある（`web_safari` と `android` の両方）。
だからサーバーは映像を中継しない。
URL を返すだけでよい。

**素の GET での確認だけはクライアントに残す。**
確かめたいのは「この回線から取れるか」であり、サーバーで確かめると別の回線の話になる。
再生するのは手元の VRChat なので、手元から叩いて初めて同じ問いになる。
IP に紐づく形が将来出てきたときも、ここで 403 を見て候補から落とせる。
つまりこの確認は、上の前提が崩れたことに気付くための見張りでもある。

## 要求と応答

### `POST /resolve`

```http
POST /resolve HTTP/1.1
Content-Type: application/json

{
  "url": "https://www.youtube.com/watch?v=dQw4w9WgXcQ",
  "client": "web_safari"
}
```

| 欄 | 型 | 内容 |
|---|---|---|
| `url` | string | 必須。`http` と `https` のみ受ける |
| `client` | string | 必須。`yt-dlp` の `player_client` にそのまま渡る名前 |

**欄の名前は、ここに書いたとおりの小文字で送る。**
サーバーは大文字小文字を区別するので、`Url` や `videoUrl` は「無い」ものとして扱われる。

型付きの言語から投げるなら、シリアライザの既定に任せない。
たとえば .NET の `JsonSerializer.Serialize(record)` はプロパティ名をそのまま出すので、`Url` と `Client` になる[^pascal]。

中継するものを書くときも、**受けた本文をそのまま流すか、送る形を明示して組み直すか**のどちらかにする。
受けと送りで別の既定が効いていると、片方だけが崩れる。

[^pascal]: 間に立つ API の受け側が大文字小文字を無視する実装だと、その API 自身は要求を読めるのに、**転送だけ**が `{"Url": …}` になり、resolver は `url is required` を返す。
    往復させる試験は**同じ既定で直列化して解析し直す**ため、食い違いが打ち消し合って素通りする。
    線の上に出た本文の側でキーを見ないと捕まらない。

1 リクエストが 1 回の `yt-dlp -J` に対応する。
クライアントは 3 本（`web_safari` と `android` と `default`）を並列で投げる。
`default` は `yt-dlp` の既定の組み合わせを指す名前で、音声だけの形式を返すのはいまのところこれだけである。
サーバー側でまとめない。
まとめると「どのクライアントを使うか」の規則がサーバーにも住むことになり、責任の分け方が崩れる。

応答は 200 で、`yt-dlp` の出力をそのまま返す。

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Encoding: gzip

{ ...yt-dlp の -J 出力をそのまま... }
```

加工しない。
間引くと、クライアント側の選別条件が増えたときにサーバーも直すことになる。

生 JSON は 100KB を超えるので、gzip で返す。
1 割前後まで落ちる。

### サーバーが走らせるコマンド

```
yt-dlp -J --ignore-no-formats-error --no-warnings \
  --js-runtimes deno:<deno のパス> \
  --extractor-args youtube:player_client=<client> \
  <url>
```

`--ignore-no-formats-error` を落とさない。
`-J` でも既定のフォーマット選択が走るので、それを満たせない動画では終了コードが 1 になる。
実際には使えるフォーマットがあるのに、何も取れなくなる[^noformats]。

`--js-runtimes` で deno を明示する。
PATH 任せにすると、動いているのに nsig が解けていない状態に気付けない。

**deno を置くだけでは足りない。**
署名と n challenge を解く JavaScript 本体は `yt-dlp-ejs` という別の部品で、yt-dlp には入っていない。
無いと解決が両方失敗し、`web_safari` は storyboard しか返さなくなる。
実測（yt-dlp 2026.08.19 と deno 2.9.6）:

| | formats | HLS muxed |
|---|---|---|
| `yt-dlp-ejs` 無し | 4（storyboard だけ） | 0 |
| あり | 11 | itag 91〜96（1080p まで） |

**どちらも HTTP 200 で返る。**
失敗が状態に出ないので、返ってきたフォーマットを数えるまで気付けない。

用意の仕方は 3 通りある。

| やり方 | いつ取りに行くか |
|---|---|
| **`yt-dlp-ejs` を入れておく**（pip / npm） | 組むとき。**推す** |
| yt-dlp の公式実行ファイルを使う | 同梱されているので取りに行かない |
| `--remote-components ejs:github`（または `ejs:npm`）を渡す | **要求のたびに外から** |

サーバーなら最初の 2 つのどちらかにする。
版が固定でき、要求のたびに GitHub や npm へ取りに行かずに済む。
`--remote-components` は既定で切ってあり、渡さなければ何も取りに行かない[^ejs]。

[^ejs]: 手元のクライアントが素で動くのは、公式実行ファイルを使っているため。
    キャッシュを空にしても 11 本返る。
    python の image に pip で入れただけのサーバーはこれに当たらない。

引数は配列で渡し、シェルを経由させない。
文字列連結で組み立てると、次節の検証をすり抜けたときに注入の口になる。

[^noformats]: HLS の muxed を持たない動画で起きる。

## 入力の検証

`url` も `client` も、そのまま `yt-dlp` の引数に流れる。
ここが唯一の attack surface になる。

- **`url`**：`http` と `https` のみ。`-` で始まる文字列はオプションとして解釈されるので、URL として parse できることを先に確かめる
- **`client`**：`^[a-z][a-z0-9_]{0,31}$` に一致すること

`client` を特定の名前の allowlist にはしない。
`web_safari` と `android` だけ許すと、クライアント側が 3 本目を足したときにサーバーも直さないと動かなくなる。
規則が 2 か所に住むのを避けるという前節の決め事と衝突する。
形だけ縛れば注入は防げる。

## エラーの返し方

必ず HTTP のステータスで返す。
黙って接続を切ると、クライアント側は timeout と区別が付かない。

| 状況 | ステータス | 補足 |
|---|---|---|
| `url` や `client` が形を満たさない | 400 | |
| 認証が要るのに無い、または違う | 401 | 次節 |
| 同時実行の上限に達している | 429 | `Retry-After` を付ける |
| `yt-dlp` が 0 以外で終了した | 502 | stderr の要点だけ。全文は返さない（数十行になる） |
| `yt-dlp` が時間内に終わらなかった | 504 | |

本文は JSON で返す。

```json
{ "error": "unsupported_scheme", "message": "url must be http or https" }
```

## 呼び出しを制限する

開いたまま置くと、任意の URL に対して `yt-dlp` を走らせる踏み台になる。
CPU も帯域も要求元の持ち物なので、塞がずに運用するわけにはいかない。

共有の token を `Authorization: Bearer <token>` で要求する。

```http
POST /resolve HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json
```

無いときも違うときも 401 を返す。

クライアントは token の欄を持つ（`Server.Token`）。
**空のときはヘッダを付けずに投げる。**
だから、待ち受けを localhost に寄せて SSH のトンネル越しに使うなら、サーバーは認証を実装しなくてよい。
欄を空のままにすれば同じクライアントがそのまま繋がる。

token は設定画面では伏せて出るが、設定ファイルには生のまま入る。
隠しているのは画面への映り込みまでである。
外へ出たら作り直せる形で発行する。

## 上限

| 対象 | 値 | 理由 |
|---|---|---|
| 1 回の `yt-dlp` の時間 | 60 秒 | 無いと詰まったプロセスが居座る |
| 同時に走る `yt-dlp` | CPU 数まで | 1 リクエストで 1 本。上限が無いと、数人が同時に踏んだ小さいインスタンスが落ちる |
| 要求本文の大きさ | 8KB | URL 1 本とクライアント名しか入らない |

上限に達したら待たせずに 429 を返す。
待たせると、クライアント側の timeout との二重待ちになり、何が起きているのか分からなくなる。

クライアントは 1 回の解決で 3 本を同時に投げる。
CPU が 3 つのインスタンスなら、1 人の解決だけで上限に届く。
要らない形式は、クライアント側でそのクライアントの欄を空にすれば頼まなくなる。

## 実測値から決めたこと

Ubuntu 24.04.3、x86_64、3 CPU、1966MB のインスタンスで、`yt-dlp 2026.08.19` と `deno 2.9.6` を使って測った。

| 対象 | 値 |
|---|---|
| 解決にかかる時間 | 9.7 秒（1 本目 9.72、2 本目 9.87） |
| warm-up | 無い。1 本目と 2 本目が同じ |
| 生 JSON の大きさ | `web_safari` が 66KB、`android` が 104KB |

手元では約 3 秒なので、3 倍かかっている。
nsig の解決が CPU を食うためで、CPU の数を増やせば縮む。

この数字から、**素の同期 HTTP で足りることが決まる。**
job を作って polling させたり、SSE を張ったりする必要は無い。

nginx の既定の `proxy_read_timeout` は 60 秒、Cloudflare の無料枠は 100 秒である。
9.7 秒はどちらにも当たらない。
クライアント側の待ち時間の上限は既定が 60 秒なので、6 倍の余裕がある。

warm-up が要らなかったことも効いている。
あれば「初回だけ数十秒かかる」場合の逃げ道を用意する必要があった。

受け取り方を作り直すのは、p99 が proxy の上限に近づいたときでよい。
